# v0.2 — Bun context and types (MVP)

Implements the three core components — Detector, Synthesiser, and augmented Router — to give any TypeScript file that carries a Bun signal accurate completions, working go-to-definition, and no false squiggles on Bun globals.

**Done when:** opening a bare `.ts` file with a bun shebang or `import { $ } from "bun"` produces accurate completions, no squiggles on Bun globals, and working go-to-definition — with no `tsconfig.json` or `node_modules` on disk.

## Types delivery mechanism

The `bun-types` declarations are embedded in the binary at compile time and extracted to a per-user data directory on first Bun activation.

### Embedding (build.rs)

`build.rs` walks `vendor/bun-types/` and generates `$OUT_DIR/bun_types_generated.rs`:

```rust
pub static BUN_TYPES_FILES: &[(&str, &[u8])] = &[
    ("index.d.ts",    include_bytes!("../../vendor/bun-types/index.d.ts")),
    ("bun.d.ts",      include_bytes!("../../vendor/bun-types/bun.d.ts")),
    // … one entry per .d.ts file
];
pub const BUN_TYPES_VERSION: &str = "1.x.y";  // from vendor/bun-types/package.json
```

`synthesiser.rs` includes this file with `include!(concat!(env!("OUT_DIR"), "/bun_types_generated.rs"))`.

### Extraction

Destination: `{data_dir}/bundt/bun-types-{BUN_TYPES_VERSION}/`

| Platform | `data_dir`                                       |
| -------- | ------------------------------------------------ |
| Linux    | `$XDG_DATA_HOME/bundt` or `~/.local/share/bundt` |
| macOS    | `~/Library/Application Support/bundt`            |
| Windows  | `%APPDATA%\bundt`                                |

The version string in the path acts as a cache key — if the directory already exists, extraction is skipped. A new `bundt` release with a new `bun-types` version produces a new directory; the old one is left in place (manual cleanup is fine).

The extraction is triggered once, the first time the Synthesiser is called. It is not repeated within a session.

The `types_root` in `SynthesisResult` is the path to this extraction directory (e.g. `~/.local/share/bundt/bun-types-1.x.y/`).

## TS LSP injection mechanism

### Implicit projects (no on-disk tsconfig) — US-05, US-06

`typescript-language-server` supports a `workspace/didChangeConfiguration` notification with settings that include `typescript.tsserver.implicitProjectConfig.compilerOptions`. These compiler options govern all files that tsserver places in implicit projects — files not covered by any on-disk `tsconfig.json`.

When bundt first detects Bun context in a session (either at `initialize` for a lockfile workspace, or at the first `textDocument/didOpen` for a shebang/import file), it synthesises the tsconfig and sends:

```json
{
  "jsonrpc": "2.0",
  "method": "workspace/didChangeConfiguration",
  "params": {
    "settings": {
      "typescript": {
        "tsserver": {
          "implicitProjectConfig": {
            "compilerOptions": {
              "moduleResolution": "bundler",
              "target": "ESNext",
              "lib": ["ESNext"],
              "types": ["bun-types"],
              "typeRoots": ["{types_root}"],
              "resolveJsonModule": true
            }
          }
        }
      }
    }
  }
}
```

This is sent to the downstream TS LSP (not to the IDE). It fires at most once per session — once Bun context is active, it stays active for the rest of the session.

**Timing:** the notification is sent after receiving the `initialized` notification from the TS LSP (which confirms the server is ready), or immediately before forwarding the first triggering `textDocument/didOpen`.

### Existing on-disk tsconfig — US-07 (deferred to v0.3+)

For files covered by an on-disk `tsconfig.json`, tsserver uses that project's config rather than `implicitProjectConfig`. Merging Bun settings into those projects requires a separate injection mechanism (temp-dir tsconfig with `extends`, or a per-workspace configuration override) that needs its own spike. This is deferred — the v0.2 scope covers implicit projects only.

## Router state

The v0.1 `forward` helper that handles both directions is split for v0.2:

- **IDE → TS LSP**: stateful handler (`ide_to_lsp`), owns `RouterState`
- **TS LSP → IDE**: unchanged `forward` call — all frames forwarded byte-for-byte

```rust
struct RouterState {
    workspace_root: Option<PathBuf>,
    bun_active: bool,                            // true once configuration injected
    detection_cache: HashMap<String, DetectionResult>,  // URI → last DetectionResult
}
```

`router::run` signature is unchanged; the split is internal.

## Steps

### Step 1 — Detector module (US-01, US-02, US-03, US-04) ✅ Done

New file: `src/detector.rs`. Expose via `lib.rs`.

- [x] Define `Signal` enum: `Shebang`, `BunImport`, `Lockfile`
- [x] Define `DetectionResult` enum: `Inactive`, `Active { signal: Signal }`
- [x] Implement `pub fn detect(file_content: &str, workspace_root: Option<&Path>) -> DetectionResult`
  - **Shebang**: first line of `file_content` is exactly `#!/usr/bin/env bun` (no leading whitespace, no extra args)
  - **BunImport**: string scan for any of:
    - `from "bun"` or `from 'bun'` (import/export)
    - `import "bun"` or `import 'bun'`
      `require("bun")` is not a match
  - **Lockfile**: `workspace_root.join("bun.lockb")` exists as a file; if `workspace_root` is `None`, skip; if `fs::metadata` fails for a reason other than NotFound, treat as absent and log at debug level
  - Evaluate in order: Shebang → BunImport → Lockfile; return on first match

**Unit tests** (`src/detector.rs`):

- First line `#!/usr/bin/env bun` → `Active { Shebang }`
- Shebang on second line only → not Shebang (check BunImport/Lockfile fall-through)
- `#!/usr/bin/env bun --smth` → not Shebang (extra arg)
- `import { $ } from "bun"` → `Active { BunImport }`
- `import "bun"` → `Active { BunImport }`
- `export { foo } from "bun"` → `Active { BunImport }`
- `import { foo } from "bun-utils"` → not BunImport (prefix match false positive guard)
- `require("bun")` → not BunImport
- `bun.lockb` present at workspace_root → `Active { Lockfile }`
- `workspace_root` is `None` → Lockfile not triggered
- Empty content, no workspace → `Inactive`
- Shebang + bun import: Shebang wins (priority order)
- BunImport + lockfile: BunImport wins (priority order)

**Manual verification**

```bash

```

All tests pass. No binary-level verification is possible until the detector is wired into the router in Step 4.

### Step 4 — Router: `initialize` interception (US-03, workspace root capture) ✅ Done

Expand `router.rs`:

- [x] Add `RouterState` struct (see above)
- [x] Split `router::run` into `ide_to_lsp(ide_in, lsp_in)` (stateful, owns `RouterState`) and retain `forward(lsp_out, ide_out, "LSP→IDE")` unchanged
- [x] In `ide_to_lsp`, on each frame:
  - Parse JSON; on error: log + skip (same behaviour as v0.1)
  - Dispatch by `method` field; default: forward byte-for-byte
- [x] On `initialize`:
  - Extract `params.rootUri` (or `params.rootPath` as fallback); convert to `PathBuf`; store as `state.workspace_root`
  - Run `detect("", Some(&workspace_root))` to check for lockfile-only activation (content is empty because no file is open yet; only Lockfile signal can fire)
  - If `Active { Lockfile }`: call `synthesise`, store result, set `state.bun_active = true`, store synthesis as `state.pending_synthesis`
  - Forward the (unmodified) `initialize` frame to the TS LSP

  **Timing resolved:** `workspace/didChangeConfiguration` is sent after the `initialized` notification from the IDE (not immediately after `initialize`). Intercepting `initialized` and piggybacking the configuration at that point is the correct approach — it guarantees the server has completed its initialisation handshake before receiving configuration. The `pending_synthesis` field bridges the gap between the two handlers.

- [x] On `initialized` (from IDE → LSP): if `state.bun_active` and `state.pending_synthesis` is set, send `workspace/didChangeConfiguration` to TS LSP, clear `pending_synthesis`, then forward `initialized`

- `initialize` with `rootUri` not containing `bun.lockb` → `bun_active` not set; `initialize` forwarded unchanged
- `initialize` with no `rootUri` → `workspace_root` is `None`; no crash
